# تأمين إعدادات أنواع الطلبات

## نطاق الإصلاح

تحويل شاشة `/requests/setup` من الكتابة المباشرة إلى RPC للقراءة والحفظ.
وظيفتا `get_request_type_settings` و`save_request_type_settings` تتحققان من
`auth.uid()` ودور `admin` الفعلي في `user_roles` باستخدام `is_permissions_admin()`.
اختيار «إداري» عند التسجيل لا يمنح هذه الصلاحية.

- سياسة RLS **restrictive** تمنع الوصول المباشر لقسم `request_types`، حتى مع بقاء سياسة demo القديمة.
- `USING` و`WITH CHECK` يحميان نقل السجل من/إلى القسم؛ المدير أيضًا يحفظ عبر RPC فقط.
- لا حذف أو إعادة كتابة للبيانات القديمة أثناء الترحيل.
- تحقق خادمي من الحقول، الأكواد المكررة، مسار الاعتماد، SLA وحدود حجم القائمة.
- الحفظ يقارن القيمة الأصلية تحت قفل، بما يشمل أول إنشاء؛ تعديل مديرين من نفس النسخة ينتج نجاحًا واحدًا وتعارضًا واحدًا.
- لا قيم افتراضية عند فشل القراءة أو تلف السجل. المقترحات الافتراضية تظهر فقط عند تأكيد عدم وجود إعدادات محفوظة.
- فصل المسودات والتخزين حسب المستخدم؛ إيقاف التعديل حتى اكتمال التحميل، وبعد أي نتيجة حفظ غير مؤكدة لحين إعادة التحميل.
- إدخال سلسلة الموافقات يُحتفظ به كنص أثناء الكتابة ويُحلّل عند الحفظ فقط.

## النشر المطلوب — قاعدة البيانات قبل الواجهة

1. انسخ البيانات احتياطيًا، وتحقق على staging من وجود مستخدم موثوق بدور `admin` فعلي؛ لا تمنح الدور اعتمادًا على بيانات التسجيل.
2. طبّق `supabase/migrations/20260915100000_secure_request_type_settings.sql`.
   يعتمد على ترحيل الصلاحيات السابق ووجود `app_settings`؛ لا يحتاج تفعيل منطق الشركات.
3. اختبر مديرًا وموظفًا وزائرًا: المدير يقرأ/يحفظ عبر RPC، وغير المدير يُرفض، والوصول المباشر للقسم ممنوع للجميع.
4. اختبر فتح تبويبين والتعديل المتزامن، وإعادة التحميل بعد التعارض، وفقد الشبكة، والسجل التالف.
5. انشر الواجهة بعد نجاح التحقق. لو وصلت الواجهة أولًا، تتوقف عن الحفظ وتعرض رسالة الترحيل المطلوب؛ لا ترجع للكتابة غير المحمية.

الترحيل وحده لا يثبت أن قاعدة الإنتاج طبّقته. لا يُعتبر الإغلاق الأمني مكتملًا
قبل التحقق من ACL/RLS ومن أدوار المستخدمين في قاعدة الهدف.
الرجوع لكود الواجهة القديم لن يعيد الحفظ المباشر بعد الترحيل؛ احتفظ بوظائف RPC والسياسة الواقية.
لا تُزل السياسة الواقية كحل لتشغيل عميل قديم.

## الاختبارات

`npm test` يشغّل اختبارات قواعد الطلبات وعقد استجابات RPC وحالات الفشل وفحوصًا ثابتة للواجهة.
GitHub Actions يشغّل أيضًا PostgreSQL 16 مؤقتًا، يطبق **ترحيل الصلاحيات الفعلي** ثم ترحيل هذا الإصلاح،
ويختبر RLS والحفظ وتنافس جلستين. ملفات `tests/sql` fixtures مخصصة لقاعدة مؤقتة فقط، لا تُشغّل على staging أو production.
هذه الاختبارات لا تختبر Supabase الإنتاجي ولا تعتبر UAT للواجهة.

## حدود يجب عدم إخفائها

- الإعدادات ما زالت عامة على مستوى النظام، وليست tenant-scoped. لا تصلح بعد لاختلاف مسارات شركات مستقلة.
- حماية هذه الخطوة تخص `request_types` فقط. سياسات أقسام `app_settings` الأخرى والجداول القديمة لم تتغير وما زالت تحتاج معالجة مستقلة؛ لا تضع فيها أسرارًا.
- هذا إعداد للمسارات وليس محرك تنفيذ للموافقات أو SLA أو الإشعارات. لا يوجد Realtime للموافقات.
- لا سجل تاريخ immutable لإعدادات الطلبات بعد؛ الحفظ المشروط يمنع ضياع تحديث أحدث، لكنه ليس سجل تدقيق.
- ملف شركة جديد أو دور واجهة لا يمنح تلقائيًا دور مدير النظام.
